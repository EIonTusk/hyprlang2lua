Build a Hyprland config converter that translates hyprlang (the legacy `.conf`
format) to Lua (the new format introduced in Hyprland 0.55, May 2026). Ship it
as a Go CLI. A static web UI is a stretch goal once the CLI is solid.

## Priorities (do not invert)

1. **Primary: the Go CLI.** A robust, well-tested binary that handles real
   configs is the whole product. Do not start on the web UI until the CLI
   passes its test corpus.
2. **Secondary: the web UI.** Only after the CLI works end-to-end. The core
   package must already be wasm-compatible (no I/O), so the web UI is mostly
   wiring once it's time.

If you run out of time or scope, ship the CLI without the web UI. The reverse
is unacceptable.

## Context

Hyprland 0.55 deprecated hyprlang in favor of Lua. Both formats currently work
— Hyprland prefers `hyprland.lua` over `hyprland.conf` if both exist — but
hyprlang will be dropped in 1-2 releases. At least one community converter
exists (returnVoid67/Hyprland_Lua_Converter); build this from scratch using
authoritative sources rather than copying it.

## Authoritative sources (priority order)

1. **Lua stubs shipped with Hyprland** — autogenerated from source, define the
   actual Lua API. Look in hyprwm/Hyprland's `meta/` directory, or
   `/usr/share/hypr/stubs/` on a system with Hyprland installed. More
   authoritative than docs.
2. **Lua-ification announcement**: https://hypr.land/news/26_lua/
3. **0.55 release notes**: https://hypr.land/news/update55/
4. **Hyprland wiki**: https://wiki.hypr.land/Configuring/Start/
5. **The hyprlang parser source** in hyprwm/Hyprland — for variable
   substitution, escaping, comment handling, multi-line values.

Fetch these from the actual repos/sites — don't rely on memory.

## Architecture

```
/internal/converter/   — pure Go: lexer, parser, AST, Lua codegen. No I/O.
                         Exposes: Convert(src string) (lua string, report Report, err error)
/cmd/hyprlang2lua/     — CLI thin wrapper around /internal/converter (the focus)
/web/                  — static site; wasm wrapper. Stretch goal only.
```

The core package must be free of `os`, `net`, and filesystem calls. This keeps
it wasm-compatible later, and it's also just good Go architecture — the CLI
will be easier to test.

## Scope

**Phase 1 — must work (the common 80%)**
- `key = value` at top level and inside sections (`general { }`,
  `decoration { }`, `input { }`, `animations { }`, `gestures { }`, `misc { }`)
- `bind = MOD, KEY, dispatcher, args` and variants (`bindm`, `binde`, `bindr`,
  `bindl`)
- `exec`, `exec-once`
- `monitor = ...`, `windowrule = ...`, `windowrulev2 = ...`, `workspace = ...`,
  `layerrule = ...`
- User variables (`$mainMod = SUPER` → lua local) and substitution at use sites
- Comments preserved, `#` → `--`

**Phase 2 — flag clearly, never silently drop**
- `source = path.conf` (decide and document: inline-expand vs `dofile()` vs
  `require()`)
- `submap = ...` blocks
- Multi-line values and escaped commas in `exec` args
- Plugin sections (`plugin { name { } }`)
- `env =`, `envd =`
- `device { }` per-device input sections

Emit `-- TODO: manual review` for anything unhandled.

## Implementation (CLI — the main work)

- **Go 1.22+**, standard library only where possible. No parser-generator —
  hand-written recursive descent is small and readable for this grammar.
- **Real lexer + parser**, not regex substitution. Hyprlang has nested
  sections, `$var` interpolation, and escapes; regex will bite on real configs.
- **AST → Lua codegen**, not token-by-token.
- Preserve comments and rough source ordering — users will diff output against
  their original.
- Don't invent Lua APIs not present in the stubs. Passthrough comment when in
  doubt.
- CLI shape: `hyprlang2lua input.conf > output.lua`, `--dir ~/.config/hypr/`
  to walk a tree, `--report` to print coverage stats, `--check` to exit
  non-zero if anything was flagged for manual review (useful for CI).

## Verification (CLI)

Test corpus from real-world dotfile repos — this is the bar for "CLI is done":
- end-4/dots-hyprland
- HyDE-Project/HyDE
- mylinuxforwork/dotfiles
- prasanthrangan/hyprdots
- The default example config in hyprwm/Hyprland

For each: coverage % (translated / passthrough / flagged), visual diff for
sanity. Golden-file tests in `/internal/converter/testdata/` — each `.conf`
input paired with an expected `.lua` output. Fuzz the lexer with `go test
-fuzz` to catch crashes on malformed input.

If Hyprland is installable in the test env, try loading the converted config
— the only true acceptance test.

## Stretch: Web UI

Only after the CLI is solid and the corpus passes.

- Static HTML + small vanilla JS + a wasm build of the core package. No
  bundler, no framework.
- Build: `GOOS=js GOARCH=wasm go build -o web/main.wasm ./web/wasm`. Include
  the standard `wasm_exec.js` from `$(go env GOROOT)/lib/wasm/`.
- UI: two side-by-side text panes (input / output), Convert button, coverage
  report panel, "download .lua" button, drag-and-drop on input.
- Deploy via GitHub Actions to GitHub Pages on push to `main`.
- TinyGo is an option for smaller wasm but has stdlib gaps; only switch if
  stock Go's artifact is unacceptably large.

If anything about the wasm wiring fights you for more than an hour or two,
drop it and ship the CLI alone. The CLI is the product.

## Constraints

- Core package: no `os`, no `net`, no filesystem. Pure functions only.
- Start by fetching the stubs and skimming the hyprlang parser, **then**
  sketch the AST, **then** build out. Don't start with regex.
- For architectural choices (especially `source =` handling), pick one with
  reasoning rather than asking.
- Do not start the web UI until the CLI passes the corpus.
